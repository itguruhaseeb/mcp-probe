same committed instrument as the August 2026 draw (`study/2026-08/sample/`),

## What "annotations" meant, and the correction

The August write-ups (study README, arXiv 2609.10962, the MSR draft) describe
the annotation figure as the share of tools lacking `readOnlyHint`,
`destructiveHint`, `idempotentHint` or `openWorldHint`. It was not. The
harness's `annotationState()` counted a tool as missing annotations when any
lint issue's text contained the word "annotation", and the only probe message
that does is the one for a missing **title** (`tool has no "title"
annotation`). The safety-hint message does not contain the word. So every
"annotation" figure in the August artifacts, the 58.8%, the 41.5% curated
comparison, the 72 / 122 / 0 all-none-partial split and the 1.53% upper bound,
is a **title** figure.

This was found on 2026-10-01 when the full tool objects were captured for the
first time (`capture-catalog.mjs`) and the harness's per-server `missing`
count was checked against them: it equals the no-title count in 196 of 196
October servers and in 166 of 166 recountable August servers, and equals the
no-safety-hint count in only 148 and 136 respectively. The test is in
`annotation-stats.mjs` (`firstPassMetricTest`) and its result is in
`../august-recount/recount-2026-10-01.json`.

The corrected figures are in `annotations-2026-10-01.json` (October) and
`../august-recount/` (August, re-probed at pinned versions). Under the real
definition, October: 71 servers annotate every tool, 120 none, 5 partial, and
63.6% of tools carry no safety hint. The server-level picture is still close
to bimodal (97.4%), but partial servers exist and the one-sided 95% upper bound
on their prevalence is 5.3%, not 1.5%. The harness now reports both metrics by
rule id under names that say which is which (`annotations` = title, kept for
comparability; `safetyHints` = the real thing).

## How the run went, including what went wrong

The probe ran in four chunks on a 2-vCPU, 8 GB host. Four things happened
that a reader of the numbers should know about.

**A sampled server forked itself 659 times.** `tribunal` 1.3.2 failed the
handshake in chunk 1 and kept spawning after the harness killed its `npx`
parent; the harness kills the direct child only, so the grandchildren were
reparented to PID 1 and kept going. By the end of chunk 2 they held 5.5 GB
resident and chunk 2 died (exit 137). The 64 servers probed after `tribunal`
in chunks 1 and 2 were discarded and re-probed, because results obtained
under that memory pressure are not the server's. `reaper.sh` was written and
ran alongside every later chunk and both catalog passes; it reaped 18 more
orphans in all, mostly servers that outlived their `npx` parent and a few
detached install scripts (`logs/reaper.log`).

**Timeouts were host starvation, not server behaviour.** Chunk 3 ran at
concurrency 4 on 2 cores. Its last 24 results were consecutive `timeout`
exclusions whose wall times were 62 to 78 s against a 45 s kill timer, which
means the harness process itself was not being scheduled. Three of the 24
re-probed alone returned in 3 to 9 s. All 24 were discarded and re-probed in
chunk 4 at concurrency 2 with the reaper running; none timed out. **The final
table contains zero timeouts**, and the policy for this and future draws is:
a timeout observed under load is re-probed at concurrency 2 before it counts.
The August table also contains zero timeouts, so the comparison is unaffected,
but August was run at concurrency 4 and this failure mode was not known then.

**mcp-probe 0.1.2 truncates large JSON output through a pipe.** `0nmcp`
advertises 1,083 tools (525 KB of `--json`). The probe wrote it and called
`process.exit()` before the 64 KiB kernel pipe buffer drained, the harness
received unparseable JSON with exit code 0, and classified the server as
`launch-failed`. The fix (await the write) is in `bin/mcp-probe.js` with a
regression test; `0nmcp` was re-probed through the harness with the fixed
probe and is `included` (its first-pass file is kept in `logs/`). This is the
only result in the table not produced by the 0.1.2 binary. The failure
requires exit code 0 with no parseable JSON, and no other October server and
no August server (zero `launch-failed`) shows that signature. Five other
October servers with 112 to 315 tools, each well over 64 KiB of output, came
through intact because the truncation is a race between the exit and the
reader's drain, which is also why it was not caught sooner.

**A server wrote credentials into the working directory.** The probe runs
each server with the repository root as its working directory and supplies
no credentials. After the August recount, that directory contained a `.env`
and a `.mcp.json` written by `ainative-memory-mcp` 1.0.1 during its
handshake: it had auto-provisioned a cloud project on the author's behalf
and stored a temporary API key for it, with a config block instructing an
MCP host to launch it with that key. Two other servers created directories
(`.agent-memory/`, `.wayy-ops/`). None of this was committed; the files were
removed and are noted here because a "no credentials supplied" probe can
still end up holding credentials a server minted for itself, and because
anyone re-running the probe should do so in a disposable directory.

Two more instrument fixes came out of the catalog pass: the linter threw on
`annotations: null` (now treated as absent), and the aggregator's one-sided
upper bound was computed with the k=0 formula for every k (now
Clopper-Pearson; the August value, k=0, is unchanged).

## Reproduce

```sh
# from the repository root, with the October frame from the deposit
node study/2026-08/sample/draw-sample.mjs --frame candidates-registry-2026-10-01.json --seed 20261001 --n 400 --out sample.json
node study/2026-08/sample/probe-sample.mjs --sample sample.json --probe-root . --out results/ --concurrency 2
node study/2026-08/sample/aggregate-sample.mjs --in results/ --sample sample.json --out summary.json
node study/2026-10/sample/make-outcome-table.mjs --sample sample.json --in results/ --out study.tsv
node study/2026-10/sample/capture-catalog.mjs --sample sample.json --results results/ --probe-root . --out catalog/
node study/2026-10/sample/annotation-stats.mjs --catalog catalog/ --out annotations.json
```

The draw regenerates exactly from the frame. The probe does not: packages are
unpinned (`npx -y <pkg>`), so a re-run probes whatever version npm resolves
that day, and a server's tool list can depend on its environment. Treat a
re-run as a new observation of the same sample, not a check of this one; the
catalog pass is the check that this one is internally consistent (196 of 196
second-pass tool counts equalled the first pass).
